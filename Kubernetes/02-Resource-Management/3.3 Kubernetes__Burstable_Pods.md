### 🔍 YAML Breakdown

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nnappone
  namespace: learning
  labels:
    app: nnappone
spec:
  containers:
    - name: crackone-app
      image: nginx
      resources:
        requests:
          memory: "150Mi"   # ← Minimum guaranteed
        limits:
          memory: "250Mi"   # ← Maximum allowed
# ❌ No CPU resources defined!

```

> 🔍 Key Observation:
> 
> - Only **memory** has `requests` and `limits`
> - **CPU** has **no resources defined**
> → This is **enough** to make the Pod **Burstable** (not BestEffort, not Guaranteed)

---

### 📌 What Makes a Pod "Burstable"?

A Pod is **Burstable** if **at least one** of these is true:

- It has **`requests` ≠ `limits`** for any resource (e.g., memory: 150Mi ≠ 250Mi), **OR**
- It has **`requests` or `limits` defined for only some resources** (e.g., memory defined, but CPU missing)

> ✅ Your Pod qualifies because:
> 
> - Memory: `requests (150Mi)` < `limits (250Mi)` → **burst allowed**
> - CPU: **not defined** → treated as **BestEffort for CPU**, but **Burstable overall**

> 🎯 Kubernetes Rule:
> 
> 
> **Burstable = Not BestEffort AND Not Guaranteed**
> 

---

### 🆚 QoS Comparison (Memory Focus)

| QoS Class | Memory `requests` | Memory `limits` | CPU Defined? | Eviction Priority |
| --- | --- | --- | --- | --- |
| **BestEffort** | ❌ | ❌ | ❌ | 🔴 **First** |
| **Burstable** | ✅ (150Mi) | ✅ (250Mi) | ❌ | 🟡 **Medium** |
| **Guaranteed** | ✅ (e.g., 200Mi) | ✅ (=200Mi) | ✅ (equal req/lim) | 🟢 **Last** |

> 💡 Burstable Behavior:
> 
> - Gets **150Mi guaranteed** at startup (scheduler reserves this).
> - Can **burst up to 250Mi** if node has free memory.
> - If memory pressure occurs:
>     - Evicted **after** BestEffort Pods
>     - Evicted **before** Guaranteed Pods
>     - Among Burstable Pods: those **using more than requested** are killed first.

### 💡 Real-World Use Case for Burstable

Most **web apps**, **APIs**, and **stateless services** use **Burstable** because:

- They have **baseline usage** (e.g., 150Mi idle)
- But need to **handle traffic spikes** (burst to 250Mi)
- Don’t require **strict guarantees** (like databases might)

> ✅ Best practice:
> 
> 
> Always set **at least memory `requests`** → avoids BestEffort, improves scheduling.
>

### ❓ Common Questions

**Q: What if I define CPU but not memory?**

A: Still **Burstable**! As long as **any resource** has `requests`/`limits`, it’s not BestEffort.

**Q: Can I have Burstable with only `requests` (no `limits`)?**

A: **Yes!** Example:

```yaml
resources:
  requests:
    memory: "128Mi"
# No limits → still Burstable

```

> ⚠️ But not recommended — without limits, a memory leak could crash the node!
> 

**Q: Why is CPU missing here?**

A: The author focused on **memory QoS**. In practice, define **both**:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"

```

### ➡️ Summary

✅ **Burstable** = flexible resource usage with **baseline guarantee**.

✅ Triggered by:

> requests < limits, ORPartial resource definition (e.g., memory only)
⚠️ Safer than BestEffort, but less protected than Guaranteed.
🔍 Verify with: kubectl describe pod | grep "QoS Class"
✅ Ideal for most stateless apps.
