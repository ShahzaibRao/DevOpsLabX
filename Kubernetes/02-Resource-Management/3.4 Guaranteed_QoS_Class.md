### 🔍 YAML Breakdown

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nnappone
  namespace: learning
  labels:
    app: nnappone
spec:
  containers:
    - name: crackone-app
      image: nginx
      resources:
        requests:
          memory: "250Mi"
          cpu: "400m"
        limits:
          memory: "250Mi"   # ← Same as requests!
          cpu: "400m"       # ← Same as requests!

```

> ✅ Key Observation:
> 
> 
> For **every container** and **every resource** (CPU + memory):
> 
> **`requests == limits`**
> 

> 🎯 This is the ONLY requirement for Guaranteed QoS.
> 

---

### 📌 What Is "Guaranteed" QoS?

A Pod gets **Guaranteed** QoS **if and only if**:

- Every container in the Pod defines **both `requests` and `limits`** for **CPU and memory**, **AND**
- For **each resource**, `requests == limits`

> 💡 Why "Guaranteed"?
> 
> 
> Kubernetes **reserves exactly 400m CPU + 250Mi memory** on a node **before scheduling**.
> 
> The Pod will **never be starved** of these resources (as long as the node is healthy).
> 

---

### 🆚 Full QoS Comparison

| QoS Class | CPU `req == lim`? | Memory `req == lim`? | Eviction Priority | Use Case |
| --- | --- | --- | --- | --- |
| **BestEffort** | ❌ Not defined | ❌ Not defined | 🔴 **First** | Debug pods, labs |
| **Burstable** | ❌ (or missing) | ❌ (or missing) | 🟡 **Medium** | Web apps, APIs |
| **Guaranteed** | ✅ **Yes** | ✅ **Yes** | 🟢 **Last** | Databases, monitoring, critical services |

> 🛡️ Guaranteed Pods are NEVER evicted due to resource pressure — unless the node itself fails.
>

### 💡 When to Use Guaranteed QoS?

✅ **Critical stateful workloads**:

- Databases (MySQL, PostgreSQL, Redis)
- Monitoring agents (Prometheus, Fluentd)
- Real-time systems (trading, telecom)

✅ **Predictable performance required**

✅ **Cannot tolerate throttling or eviction**

> ⚠️ Trade-off:
> 
> - Uses **more cluster capacity** (no overcommit on these resources)
> - Harder to schedule if cluster is fragmented

---

### ❓ Common Questions

**Q: What if one container is Guaranteed, but another isn’t?**

A: The **entire Pod becomes Burstable** (QoS is determined by the **lowest** class among containers).

**Q: Can I omit CPU or memory?**

A: **No!** If you define `limits` for memory, you **must also define CPU limits = requests** (and vice versa) to stay Guaranteed.

**Q: Does Guaranteed mean better performance?**

A: Not necessarily — but it means **consistent, predictable** performance under load.

**Q: What about `restartPolicy`?**

A: Guaranteed Pods often use `restartPolicy: Always` (default) to ensure uptime.

### 🎯 Pro Tip: Enforce Guaranteed QoS Cluster-Wide

Use **LimitRange** to auto-set `requests = limits` for namespaces:

```yaml
apiVersion: v1
kind: LimitRange
meta
  name: enforce-guaranteed
spec:
  limits:
  - default:
      cpu: "500m"
      memory: "256Mi"
    defaultRequest:
      cpu: "500m"
      memory: "256Mi"
    type: Container

```

→ Any Pod without resources gets **Guaranteed** by default!
