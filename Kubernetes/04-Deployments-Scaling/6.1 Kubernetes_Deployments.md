# 6.1: Your First Deployment (`deployment-one.yml`)

https://drive.google.com/file/d/1oUzRfeaB33aht95JwtJKTa7A0d7VrXtB/view?usp=sharing

### 🔍 YAML Breakdown

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nnwebserver
spec:
  selector:
    matchLabels:
      run: nnwebserver          # ← Must match Pod template labels
  replicas: 2                   # ← Run 2 identical Pods
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1             # ← Allow 1 extra Pod during update
      maxUnavailable: 0       # ← Keep all Pods available during update
  template:
    metadata:
      labels:
        run: nnwebserver       # ← Labels for Pods (must match selector!)
    spec:
      containers:
        - name: nnwebserver
          image: lovelearnlinux/webserver:v2
          livenessProbe:       # ← Health check
            exec:
              command: ["cat", "/var/www/html/index.html"]
            initialDelaySeconds: 10
            periodSeconds: 20
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "200m"
              memory: "256Mi"
          ports:
            - containerPort: 80

```

### 📌 Why Use a Deployment (vs Bare Pod)?

| Feature | Bare Pod | Deployment |
| --- | --- | --- |
| **Replication** | ❌ 1 Pod only | ✅ `replicas: N` |
| **Self-healing** | ❌ Dies forever | ✅ Restarts failed Pods |
| **Rolling Updates** | ❌ Manual | ✅ Zero-downtime updates |
| **Rollback** | ❌ Impossible | ✅ `kubectl rollout undo` |
| **Scaling** | ❌ Manual | ✅ `kubectl scale` |

> ✅ Deployments manage ReplicaSets, which manage Pods → 3-layer controller pattern.
> 

---

### 🔑 Key Concepts Explained

### 1. **`selector.matchLabels`**

- **Must exactly match** `template.metadata.labels`
- **Immutable** after creation → don’t change it!

### 2. **RollingUpdate Strategy**

- **`maxSurge: 1`** → During update, allow **1 extra Pod** (total = 3)
- **`maxUnavailable: 0`** → **Zero downtime** (always keep 2 Pods running)

> 🎯 Result:
> 
> - Update starts → 3 Pods (2 old + 1 new)
> - After new Pod is ready → kill 1 old → 3 Pods (1 old + 2 new)
> - Repeat until all updated

### 3. **Liveness Probe**

- Checks if app is **alive**
- If fails → **restart container**
- Uses `exec` to check if `index.html` exists

> 💡 Best Practice:
> 
> 
> Also add **`readinessProbe`** to control traffic routing!
> 

### 4. **Resource Requests/Limits**

- Required for **HPA** (Horizontal Pod Autoscaler)
- Enables **QoS classes** (Burstable in this case)

### 🧪 k3s Lab: Deploy, Scale, and Update

### 🔧 Step 1: Deploy the Application

```bash
# Apply Deployment
kubectl apply -f deployment-one.yml

# Check status
kubectl get deployments
kubectl get pods -l run=nnwebserver -o wide

# ✅ Expected: 2 Pods running on your k3s nodes

```

### 🔧 Step 2: Inspect the Controller Hierarchy

```bash
# Deployment → ReplicaSet → Pods
kubectl get rs -l run=nnwebserver
# NAME                      DESIRED   CURRENT   READY
# nnwebserver-<hash>        2         2         2

kubectl get pods --show-labels
# Labels include: run=nnwebserver, pod-template-hash=<hash>

```

> 🔍 pod-template-hash = auto-added by ReplicaSet to track versions.
> 

### 🔧 Step 3: Scale Manually

```bash
# Scale to 3 replicas
kubectl scale deployment nnwebserver --replicas=3

# Verify
kubectl get pods -l run=nnwebserver

```

> ⚠️ Don’t scale the ReplicaSet directly!
> 
> 
> Deployment will **override** it to match `spec.replicas`.
> 

### 🔧 Step 4: Trigger a Rolling Update

> 💡 Change image from v2 → v1 (or vice versa)
> 

```bash
# Edit YAML: image: lovelearnlinux/webserver:v1
kubectl apply -f deployment-one.yml

# Watch rollout
kubectl rollout status deployment nnwebserver

# Check history
kubectl rollout history deployment nnwebserver

```

> 🔍 Observe:
> 
> - New ReplicaSet created
> - Old ReplicaSet scaled down gradually
> - **Zero downtime** (thanks to `maxUnavailable: 0`)

### 🔧 Step 5: Clean Up

```bash
kubectl delete deployment nnwebserver

```

### 💡 Pro Tips for k3s

1. **Always set resource requests** → required for HPA and scheduling.
2. **Use `readinessProbe`** to avoid sending traffic to unready Pods:
    
    ```yaml
    readinessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 5
    
    ```
    
3. **Add `strategy.type: Recreate`** for stateful apps that can’t run multiple versions.

### ❓ Common Questions

**Q: What if I change the `selector` after creation?**

A: ❌ **Forbidden!** You’ll get: `"selector does not match template labels"`.

**Q: Why use `run` label instead of `app`?**

A: `run` is fine — but **`app.kubernetes.io/name`** is [recommended](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/) for production.

**Q: What happens if liveness probe fails?**

A: Container is **killed and restarted** (check `kubectl describe pod` for `Liveness probe failed`).

**Q: Can I pause a rollout?**

A: ✅ Yes!

```bash
kubectl rollout pause deployment nnwebserver
# Make changes...
kubectl rollout resume deployment nnwebserver

```

### ➡️ Summary

✅ **Deployments** = **replicated, self-healing, updatable** apps.

✅ **`selector` must match `template.labels`**.

✅ **RollingUpdate** with `maxUnavailable: 0` = **zero downtime**.

✅ **Liveness probes** restart unhealthy containers.

🔍 In k3s: Works identically to upstream Kubernetes.
