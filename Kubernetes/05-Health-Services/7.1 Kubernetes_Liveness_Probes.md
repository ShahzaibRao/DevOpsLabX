# 7.1: Liveness Probes (Auto-Restart Unhealthy Pods)

https://drive.google.com/file/d/1ovRvqFddKp74eItuM_PUL61xBU4vIzsV/view?usp=sharing

### 🔍 YAML Breakdown

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nnwebserver
spec:
  containers:
    - name: nnwebserver
      image: lovelearnlinux/webserver:v1
      livenessProbe:
        exec:
          command: ["cat", "/var/www/html/index.html"]  # ← Check if file exists
        initialDelaySeconds: 10   # ← Wait 10s before first check
        timeoutSeconds: 3         # ← Fail if check takes >3s
        periodSeconds: 20         # ← Repeat every 20s
        failureThreshold: 3       # ← Fail 3 times → restart container
      resources:
        requests:
          cpu: "500m"
          memory: "128Mi"
        limits:
          cpu: "1000m"
          memory: "256Mi"
      ports:
        - containerPort: 80

```

> 🔑 Key Insight:
> 
> 
> This probe **restarts the container** if `/var/www/html/index.html` is missing or unreadable.
> 

---

### 📌 How Liveness Probes Work

| Parameter | Purpose | Your Value |
| --- | --- | --- |
| **`exec.command`** | Run command inside container | `cat /var/www/html/index.html` |
| **`initialDelaySeconds`** | Wait before first probe | `10s` (lets app start) |
| **`periodSeconds`** | How often to probe | `20s` |
| **`failureThreshold`** | Consecutive failures before restart | `3` |
| **`timeoutSeconds`** | Max time for probe to complete | `3s` |

> 🎯 Failure Timeline:
> 
> - `t=10s`: First probe
> - If fails → `t=30s`: Second probe
> - If fails → `t=50s`: Third probe
> - If fails → **container restarted** at `t=50s`

> 💡 Probe Types:
> 
> - **`exec`**: Run command (your example)
> - **`httpGet`**: HTTP request (e.g., `GET /health`)
> - **`tcpSocket`**: Open TCP connection (for non-HTTP apps)

### 🧪 k3s Lab: Break the App & Watch Auto-Restart

### 🔧 Step 1: Deploy the Pod

```bash
# Apply Pod
kubectl apply -f pod-with-health-check.yml

# Verify it's running
kubectl get pods nnwebserver

```

### 🔧 Step 2: Simulate App Failure

> 💡 Delete the critical file that the probe checks:
> 

```bash
# Remove index.html (breaks the app)
kubectl exec nnwebserver -- rm /var/www/html/index.html

```

### 🔧 Step 3: Watch Kubernetes Heal Itself

```bash
# Watch Pod restarts
kubectl get pods nnwebserver -w

# ✅ Expected:
# NAME          READY   STATUS    RESTARTS   AGE
# nnwebserver   1/1     Running   0          10s
# nnwebserver   1/1     Running   1          45s  ← Restarted!

# Check logs to confirm
kubectl describe pod nnwebserver | grep -A 5 "Liveness"
# Events:
#   Warning  Unhealthy  50s  kubelet  Liveness probe failed: cat: /var/www/html/index.html: No such file or directory
#   Normal   Killing    50s  kubelet  Container nnwebserver failed liveness probe, will be restarted

```

> 🔍 Why did it restart?
> 
> - Probe failed 3 times (`failureThreshold: 3`)
> - Kubernetes **killed and restarted** the container
> - New container recreates `/var/www/html/index.html` (assuming image does this on startup)

### 🔧 Step 4: Clean Up

```bash
kubectl delete pod nnwebserver

```

### 💡 Real-World Liveness Probe Examples

| App Type | Probe Command |
| --- | --- |
| **Web Server** | `httpGet: { path: /health, port: 80 }` |
| **Database** | `exec: { command: ["pg_isready", "-h", "localhost"] }` |
| **Queue Worker** | `tcpSocket: { port: 6379 }` (Redis) |
| **Custom App** | `exec: { command: ["/app/health-check.sh"] }` |

> ✅ Best Practices:
> 
> - **Don’t use liveness probe for startup delays** → use `initialDelaySeconds`
> - **Make probe lightweight** → avoid heavy DB queries
> - **Test failure scenarios** → ensure restart actually fixes the issue

### ❓ Common Questions

**Q: What’s the difference between liveness and readiness probes?**

A:

- **Liveness**: "Is the app alive?" → **restart if dead**
- **Readiness**: "Is the app ready for traffic?" → **remove from Service if not ready**

**Q: Can I use both probes together?**

A: ✅ **Yes!** (You’ll see this in `pod-readiness-liveness-probes`)

**Q: What if the probe command doesn’t exist in the container?**

A: Probe fails → container restarts (check `kubectl describe pod` for `executable file not found`)

**Q: Does restarting the container lose data?**

A: ⚠️ **Yes!** If data is stored in the container filesystem (not PersistentVolume).

✅ **Fix**: Use **PersistentVolumes** for stateful apps.

### ➡️ Summary

✅ **Liveness probe** = auto-restart unhealthy containers

✅ **`failureThreshold: 3`** = 3 consecutive failures before restart

✅ **`exec` probe** = run command inside container

🔍 In k3s: Test by **deleting a critical file** → watch restart

🛠️ Always set **realistic timeouts and delays**
