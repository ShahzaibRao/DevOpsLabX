# 8.4: CPU-Only LimitRange

https://drive.google.com/file/d/1o2eUiyAj-6naAc3IJXsSbSnRqvgzWz8H/view?usp=sharing

### 🔍 YAML Breakdown

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: cpu-limit-range
  namespace: learning
spec:
  limits:
  - default:              # ← CPU limit if not specified
      cpu: 1              # = 1000m (1 full core)
    defaultRequest:       # ← CPU request if not specified
      cpu: 0.4            # = 400m (0.4 cores)
    type: Container

```

> 🔑 Key Insight:
> 
> 
> This LimitRange **only manages CPU** — memory is **not constrained** (Pods can use any memory unless restricted elsewhere).
> 

> 💡 Why CPU-only?
> 
> - **CPU is compressible**: Throttled when exceeded (no crash)
> - **Memory is incompressible**: OOMKilled when exceeded
> → Teams often **treat them differently**

---

### 📌 How CPU Units Work

| Format | Meaning | Equivalent |
| --- | --- | --- |
| `1` | 1 CPU core | `1000m` |
| `0.4` | 0.4 CPU cores | `400m` |
| `500m` | 500 milliCPU | `0.5` |

> ✅ Best Practice:
> 
> 
> Use **`m` (millicores)** for clarity:
> 
> ```yaml
> defaultRequest:
>   cpu: "400m"
> default:
>   cpu: "1000m"
> 
> ```
> 

> ⚠️ Your YAML uses decimals (0.4, 1) → valid, but m is more explicit.
>

### 🧪 k3s Lab: Test CPU-Only LimitRange

### 🔧 Step 1: Create Namespace & Apply LimitRange

```bash
# Create namespace
kubectl create namespace learning

# Apply LimitRange
kubectl apply -f namespace-cpu-limitrange.yaml

# Verify
kubectl describe limitrange cpu-limit-range -n learning
# Type       Resource  Min  Max  Default Request  Default Limit
# Container  cpu       -    -    400m               1

```

### 🔧 Step 2: Deploy Pod with NO CPU Resources

```yaml
# pod-no-cpu.yaml
apiVersion: v1
kind: Pod
meta
  name: no-cpu-pod
  namespace: learning
spec:
  containers:
  - name: nginx
    image: nginx

```

```bash
kubectl apply -f pod-no-cpu.yaml

# Check applied CPU resources
kubectl get pod no-cpu-pod -n learning -o jsonpath='{.spec.containers[0].resources}'
# ✅ Output:
# {"limits":{"cpu":"1"},"requests":{"cpu":"0.4"}}

```

> 🔍 Result:
> 
> 
> LimitRange **auto-applied CPU defaults** → Pod has **400m request, 1000m limit**
> 

### 🔧 Step 3: Deploy Pod with Custom CPU (Within Implicit Max)

```yaml
# pod-custom-cpu.yaml
apiVersion: v1
kind: Pod
meta
  name: custom-cpu-pod
  namespace: learning
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      requests:
        cpu: "600m"
      limits:
        cpu: "1500m"   # > default limit, but no max defined → allowed!

```

```bash
kubectl apply -f pod-custom-cpu.yaml
# ✅ Success! (No max defined → no enforcement)

```

> ⚠️ Critical Observation:
> 
> 
> Your LimitRange **does NOT define `max`** → Pods can request **unlimited CPU**!
> 
> → This is **risky in production** (use `max` to cap usage).
> 

### 🔧 Step 4: Add `max` to Prevent Abuse (Recommended Fix)

```yaml
# Improved LimitRange (with max)
spec:
  limits:
  - default:
      cpu: "1000m"
    defaultRequest:
      cpu: "400m"
    max:                # ← ADD THIS!
      cpu: "2000m"      # Max 2 cores per container
    type: Container

```

### 🔧 Step 5: Clean Up

```bash
kubectl delete pod --all -n learning
kubectl delete limitrange cpu-limit-range -n learning
kubectl delete namespace learning

```

### 💡 Real-World CPU LimitRange Strategies

| Workload Type | `defaultRequest` | `default` | `max` | Why |
| --- | --- | --- | --- | --- |
| **Web Server** | 100m | 500m | 1000m | Handles traffic spikes |
| **Batch Job** | 500m | 1000m | 2000m | CPU-intensive, short-lived |
| **ML Inference** | 1000m | 2000m | 4000m | Needs consistent CPU |
| **Sandbox** | 50m | 100m | 500m | Prevents resource hogging |

> ✅ Best Practices:
> 
> - **Always set `max`** in production
> - Use **millicores (`m`)** for clarity
> - **Monitor CPU usage** (`kubectl top pods`) to tune defaults

---

### 🆚 CPU vs Memory LimitRange

| Aspect | **CPU LimitRange** | **Memory LimitRange** |
| --- | --- | --- |
| **Enforcement** | Throttling (no crash) | OOMKilled (crash) |
| **Default Strategy** | Lower request, higher limit (bursting) | Request ≈ limit (no bursting) |
| **Units** | Cores or millicores (`1` or `1000m`) | Bytes (`Mi`, `Gi`) |
| **Risk of No Max** | High CPU usage → node slowdown | High memory → node OOM |

### ❓ Common Questions

**Q: What if I mix CPU and memory in one LimitRange?**

A: ✅ **Yes!** (Like your earlier `limit-ranges.yaml`). Separating them is optional.

**Q: Does CPU limit affect scheduling?**

A: ❌ **No!** Only `requests.cpu` affects scheduling. `limits.cpu` affects **runtime throttling**.

**Q: Can I use fractional values like `0.1`?**

A: ✅ **Yes!** But `100m` is clearer than `0.1`.

**Q: What’s the smallest CPU request?**

A: **1m** (0.001 core) — but **10m+ recommended** for scheduler accuracy.
