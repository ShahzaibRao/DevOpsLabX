# 13.1 : What Is Ingress? (The Kubernetes Front Door)**

### 🎯 What It Is

An **Ingress** is a Kubernetes resource that **manages external HTTP/S access** to services in your cluster — typically via **hostnames, paths, and TLS**.

> ✅ Without Ingress: You’d need NodePort or LoadBalancer for every service.
> 
> 
> 🔒 **With Ingress**: One entry point routes traffic to many services.
> 

### 💡 Real-World Analogy

> Like a reception desk in an office building:
> 
> - Visitor says: “I’m here for **marketing**” → sent to **floor 3**
> - Visitor says: “I’m here for **engineering**” → sent to **floor 5**
> - The building has **one front door** (Ingress), but many internal offices (Services)

---

### 🧪 Example: Expose Two Apps via One Ingress

**Assume you have:**

- A `web` Service (`app: web`)
- An `api` Service (`app: api`)

**Step 1: Create an Ingress Resource**

```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
meta
  name: main-ingress
  namespace: default
spec:
  rules:
  - host: web.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web
            port:
              number: 80

  - host: api.example.com
    http:
      paths:
      - path: /v1
        pathType: Prefix
        backend:
          service:
            name: api
            port:
              number: 80

```

Apply it:

```bash
kubectl apply -f ingress.yaml

```

✅ **Result**:

- `http://web.example.com` → `web` Service
- `http://api.example.com/v1` → `api` Service

> ⚠️ But wait! This won’t work yet — you need an Ingress Controller (next topic).
>

### ✅ Summary YAML

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
meta
  name: my-ingress
spec:
  rules:
  - host: myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: my-service
            port:
              number: 80

```

> 🔑 Key Fields:
> 
> - `host`: Domain name (optional — can omit for catch-all)
> - `pathType`: `Prefix`, `Exact`, or `ImplementationSpecific`
> - `backend.service`: Where to route traffic

### ❓ Common Questions

**Q: Does Ingress work out-of-the-box in k3s?**

✅ **Yes!** k3s includes **Traefik** as the default Ingress Controller.

**Q: Can I use Ingress for TCP/UDP (non-HTTP)?**

❌ No! Ingress is **HTTP/S only**.

✅ Use **Service `type: LoadBalancer`** or **Ingress Controller extensions** (e.g., Traefik TCP routers).

**Q: What’s the difference between Ingress and Service `type: LoadBalancer`?**

➡️ **LoadBalancer**: One public IP per service

➡️ **Ingress**: One public IP for **many services** (L7 routing)

**Q: Do I need TLS for Ingress?**

❌ No — but **always use it in production** (next topic).

---

### 🛠️ Best Practices

1. ✅ **Use meaningful hostnames** (`web.prod.example.com`)
2. ✅ **Prefer `pathType: Prefix`** over `Exact` for flexibility
3. ✅ **Group related services** under one Ingress resource
4. ✅ **Never expose Ingress without an Ingress Controller**
5. ✅ **Test with `curl -H "Host: web.example.com" http://<INGRESS-IP>`**
